# 第 1 步：可行性评估

> 目标环境：Windows，2GB 物理内存，弱 CPU。硬指标：常驻内存 RSS < 100MB，目标逼近 50MB。
> 本文所有数字均为**本机实测**（Windows 11 / Go 1.27.3 / 进程内自采样），不是估算。

## 1.1 技术栈选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **Go 1.20.14**（Win7 兼容的最后一个版本），`CGO_ENABLED=0` | 单文件静态 exe，无运行时 DLL 依赖；无 cgo 意味着没有额外的 C 运行时和线程库开销 |
| GUI | **手写 Win32 绑定**（user32 / gdi32 / msimg32 / comctl32 / advapi32 / psapi） | 系统原生控件 + 自绘。不引入 LCL/GTK/Qt 这类把整套控件库塞进进程的方案 |
| 文本输入 | 原生 `EDIT` 控件（仅此一处） | 免费获得 IME 中文输入、剪贴板、光标；自绘输入法成本极高 |
| 图像 | Go 标准库 `image/jpeg`、`image/png` → 32bpp DIB | **不使用 GDI+ / WIC**，避免加载系统图像编解码框架 |
| 音频输出 | **WASAPI 共享模式**（纯 COM vtable 调用，手写） | 系统 API，直通音频引擎；无需 DirectShow/Media Foundation 全家桶 |
| 音频解码 | **`github.com/hajimehoshi/go-mp3`**（纯 Go，约 6k 行） | 唯一第三方运行时依赖。纯 Go、无 cgo、分配可控，实测解码 43.9x 实时 |
| 二维码 | **`github.com/skip2/go-qrcode`**（纯 Go） | 仅登录窗口使用，渲染到 DIB 后即可释放 |
| 网易云 API | **自研**，仅用标准库 | `crypto/aes` + `math/big` 手写 weapi/RSA，`encoding/json` 流式解码；不引入 `req`、`go-ole` 等 |
| 持久化 | 单个 JSON 文件 `%APPDATA%\netmusic\config.json` | 原子写、无数据库 |

**不使用**：Electron / Wails / Tauri（WebView，最低 80–150MB 起步）、FFmpeg、Qt、GDI+、Windows Media Foundation 解码链路。

## 1.2 各组件内存占用预估 vs 实测

进程启动后各阶段实测（进程内 `GetProcessMemoryInfo` 采样，非任务管理器四舍五入）：

| 组件 | 预估 | 实测（WS） | 说明 |
|---|---|---|---|
| Go 运行时 + 二进制映像 | 3–5 MB | ~4 MB | 1 个 P 常态、4 个 P 上限 |
| 空窗口（自绘主控窗口） | 0.3 MB | **12.2 MB 整进程** | 含窗口类、字体、画刷缓存、双缓冲 DIB |
| 登录窗口（二维码 210×210） | 0.2 MB | +0.5 MB | 二维码 DIB 176KB，登录后释放 |
| 播放列表窗口（470×430） | 0.9 MB | +1.1 MB | 双缓冲 DIB 800KB + 虚拟列表 |
| 歌词窗口（400×330） | 0.6 MB | +0.6 MB | 歌词文档 ~2KB/首 |
| **音频管线** | 1–12 MB | **+13.4 MB** | 解码后整曲 PCM 不落地，只驻留**压缩后的整曲**（128kbps ≈ 1MB/首，320kbps ≈ 2.7MB/首）+ 100ms 设备缓冲 |
| 封面 1 张（98×98 DIB） | 0.04 MB | ~0.04 MB | 切歌即释放旧图 |
| **评论模块（单页）** | 0.5–3 MB | **+1.27 MB** | 见 1.4 |
| 全部 5 个窗口 + 正在播放 | — | **38–40 MB** | 含评论窗口 |

## 1.3 100MB 目标的最大风险点

按风险从高到低：

1. **WebView 方案**（Electron/Wails/Tauri）——一旦采用，任何优化都无法压到 100MB 以内。这是唯一的「一票否决」项，已彻底排除。
2. **音频解码策略**。三条路都不行/太重：
   - 全曲预解码成 PCM：一首 5 分钟 44.1kHz 立体声 = **52MB**，直接击穿预算 → **否决**；
   - FFmpeg/Media Foundation：进程会额外映射数十 MB 解码器 DLL → **否决**；
   - 流式 + 纯 Go 解码：需要 seek 能力。实测 go-mp3 的 `Seek` 是**帧精确**的（`frameStarts` 索引表，1ms 内返回），因此**保留压缩原曲 + 按需解码**成为最优解：内存 = 压缩体积（1–3MB），seek 精度和速度都满足歌词同步。
3. **评论模块**。网易云单曲评论可达 190 万条，接口单页响应 51KB（20 条）。若一次性拉取或为每条评论建控件，内存和 CPU 都会失控 → 见 1.4。
4. **Go GC 的堆上限**。默认 `GOGC=100` 在突发解析（歌单 1000 首 ≈ 1MB JSON）时可能把堆推到数十 MB 并长期不归还操作系统。对策：`debug.SetMemoryLimit(64MB)` 让 GC 更早介入，并且**所有 JSON 都从网络流直接解码**，不缓存原始响应体。

## 1.4 评论模块单独估算

- 线上数据：`limit=20` 的响应 **51,411 字节**（含 15 条热门）。
- 本项目只保留渲染所需字段（昵称/正文/点赞/时间/是否热门），**单条约 200 字节**，整页 20 条 ≈ 4KB。
- 分页拉取 + 只保留当前页 ⇒ 评论正文数据常驻 **< 100KB**。
- 真正的开销是「控件」：Win32 ListView 每行约 100–200 字节 + 控件树。因此评论列表**不使用每行一个控件的实现**，而是自绘虚拟列表（只绘制可视行），内存与评论总数**无关**。
- 预估：评论模块峰值增量 **1–3 MB**，实测 **+1.27 MB**，远低于 20MB 的降级阈值。

## 1.5 结论

**目标可行，无需放宽到 150MB。** 关键结论：

- 5 窗口全开 + 正在播放 + 评论（热门/最新分页）：**WS 38–40 MB**，约为目标的 40%。
- 评论模块增量 1.27MB，**不触发降级**（阈值 20MB），完整保留分页 + 热门/最新切换。
- 唯一的运行时第三方依赖是纯 Go 的 MP3 解码器与二维码编码器，无 cgo、无 DLL、无 WebView。

### 需要如实说明的约束

1. **操作系统版本**：Go 1.21+ 运行时要求 **Windows 10 及以上**。若目标机是 Windows 7，需要用 Go 1.20 交叉编译（代码本身兼容，仅 `debug.SetMemoryLimit` 等少数 API 需改动，见 README「Windows 7 说明」）。
2. **未登录时**只能播放免版权歌曲（`fee=0/8`）；VIP/版权曲目需要登录态（`MUSIC_U` Cookie），这是官方限制，非本项目限制。
3. 音质默认 128kbps（`standard`）。选 320kbps 时单曲驻留涨到约 2.7MB，RSS 约 +2MB，仍在预算内。
## 1.6 目标改为 Windows 7 后的修订（重要）

需求确认目标机是 **Windows 7** 后，1.1 的选型有两处必须改：

| 项 | 原方案 | 修订后 | 原因 |
|---|---|---|---|
| Go 版本 | 1.27 | **1.20.14** | Go 1.21+ 运行时要求 Win10+，编出来的 exe 在 Win7 上起不来 |
| 产物架构 | amd64 | **386 优先**（同时提供 amd64） | 2GB 内存的 Win7 机器基本都是 32 位；且 386 版在 64 位 Win7 上也能跑 |

结论不变：**目标仍然可行**，而且 32 位产物的 RSS 更好（36.3MB，私有字节从 64MB 降到 21MB）。

但 32 位带来了三类只有该架构才会出现的缺陷，已在交付版本中全部修复（详见 README「Win7 / 32 位踩过的坑」）：

1. `REFERENCE_TIME`（int64）在 32 位 stdcall 栈上占两个 4 字节槽，导致 `IAudioClient::Initialize` 参数整体错位
   → **32 位下完全没声音**；
2. `SetWindowLongPtrW` 在 32 位 user32 中不存在（SDK 宏），需运行时回退到 `SetWindowLongW`；
3. `MSG` 结构的对齐填充随架构不同，必须用 build tag 分别定义。

这三点都无法在 64 位环境里通过任何静态检查发现，只能靠**实际运行 32 位产物**（本机用 WOW64 验证）暴露。
